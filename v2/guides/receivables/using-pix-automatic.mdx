title: Using Pix Automatic
description: "Create recurrences, manage collections and attempts, and follow every step through webhooks with the V2 API."
---

**Pix Automático** lets you charge your customers on a recurring basis (subscriptions, monthly fees, services) without the payer having to authorize each charge individually. The customer authorizes the recurrence **once**, in their own bank's app, and from then on each charge (called a *collection*) is debited automatically on the agreed date, within the limits that were authorized.

On Trio, Pix Automático is made of three chained objects:

* **Recurrence (`recurrence`)**: the authorization "contract" between you and the payer. It defines periodicity, amount (fixed or variable), dates and retry rules.
* **Collection (`collection`)**: each charge occurrence generated from the recurrence (for example, October's monthly fee).
* **Attempt (`attempt`)**: each attempt to settle a collection. The same collection can have more than one attempt, according to the configured retry policy.

This guide covers the full cycle: creating the recurrence and its journey variations, settings at creation time, automatic and manual management of collections, amount updates, cancellations, queries and the webhooks fired at each step.

> All examples use the **sandbox** environment (`https://api.sandbox.trio.com.br`). In production, switch the base URL to `https://api.trio.com.br`.

### Creating a recurrence

The recurrence is created with a `POST` to the creation endpoint. Before looking at the journey variations, get to know the parameters you always need to send.

`POST: https://api.sandbox.trio.com.br/v2/in/pix/recurrences`

Required fields:

* **`bank_account_id`**: the bank account that receives the collections.
* **`counterparty`**: the payer's data. `tax_number` and `name` are required. For authorization through the app (`app` journey), the payer's `bank_account` is also required.
* **`description`**: description of the recurrence (max. 35 characters). It is shown to the payer during authorization.
* **`periodicity`**: how often the collection happens.
* **`contract_number`**: the contract/subscription number in your system (max. 35 characters).
* **`start_date`**: first day of the recurrence (ISO 8601 date, `YYYY-MM-DD`) - At least 3 days after the current date. {/* TODO(v2): verify — the "at least 3 days after the current date" rule is a V1 business rule not stated in the V2 spec */}

Possible values of **`periodicity`**:

| Value  | Meaning         |
| ------ | --------------- |
| `week` | Every week      |
| `mnth` | Every month     |
| `qurt` | Every 3 months  |
| `mian` | Every 6 months  |
| `year` | Every year      |

Relevant optional fields:

* **`end_date`**: last day of the recurrence (`YYYY-MM-DD`). If omitted, the recurrence has no end date.
* **`external_id`**: your internal reference for the recurrence.
* **`amounts`**: defines the amount (see below). If omitted, the recurrence is created with a **variable amount and no minimum**.
* **`first_payment`**: configures the first payment combined with the authorization (see the journey variations).
* **`options`**: the recurrence settings block (see the [Options and settings](#options-and-settings-at-creation) section).

#### Fixed amount vs. variable amount

The `amounts` block defines how the amount of each collection is determined:

* **Fixed amount** — send `amounts.fixed` (in cents). Every collection will have this amount and it **cannot be changed** before it is sent.
* **Variable amount with a minimum** — send `amounts.minimum` (in cents). The payer cannot authorize a limit lower than the minimum. **Each collection needs its amount informed before the collection date.**
* **Variable amount with no minimum** — omit the `amounts` block. It also requires informing the amount before each collection.

> In variable-amount recurrences, informing the amount before the collection is sent is mandatory. Use the amount update (`PUT`) or inform the `amount` when scheduling, as described in the collection management section.

#### Journey variations

Pix Automático defines different **authorization journeys**. On Trio, the resulting journey is determined by the combination of three parameters:

* **`options.authorization_type`** — `qrcode` (generates a QR Code for the payer to authorize) or `app` (sends the authorization request straight to the payer's bank app).
* **`first_payment`** — present or absent: defines whether there is a first payment combined with the authorization.
* **`first_payment.recurrence_required`** — `true` approves the recurrence and the first payment in a single authorization; `false` lets the payer pay the first payment and refuse the recurrence.

The `reference.type` field in the response indicates the channel used: `qrdn` (dynamic QR Code), `qres` (static QR Code) or `requ` (request sent to the app).

Below are the most common variations used by our customers:

**Journey A — Authorization via QR Code, fixed amount, no first payment**

The customer scans a QR Code and authorizes the recurrence. No charge is made at authorization time.

```json
{
  "bank_account_id": "018af380-cedc-3a53-29c0-e329bf0e109b",
  "counterparty": {
    "tax_number": "70004764005",
    "name": "Jhon Doe"
  },
  "description": "Monthly subscription",
  "contract_number": "CONTRACT-2025-001",
  "periodicity": "mnth",
  "start_date": "2025-11-01",
  "amounts": {
    "fixed": 4990
  },
  "options": {
    "authorization_type": "qrcode"
  }
}
```

**Journey B — Authorization + first payment combined (QR Code)**

The recurrence authorization and the first charge are approved in a single action by the payer. Useful when the subscription starts with an immediate charge. `due_detail` lets you configure the due date, interest, fine and discounts of the first payment.

```json
{
  "bank_account_id": "018af380-cedc-3a53-29c0-e329bf0e109b",
  "counterparty": {
    "tax_number": "70004764005",
    "name": "Jhon Doe"
  },
  "description": "Monthly subscription",
  "contract_number": "CONTRACT-2025-002",
  "periodicity": "mnth",
  "start_date": "2025-11-01",
  "amounts": {
    "fixed": 4990
  },
  "first_payment": {
    "amount": 4990,
    "dict_key": "pix-key-of-your-bank-account",
    "recurrence_required": true,
    "due_detail": {
      "due_date": "2025-10-25",
      "fine": {
        "calculation_type": "percentage",
        "value": 200
      },
      "interest": {
        "calculation_type": "percentage",
        "value": 100,
        "calculation_period": "month",
        "calculation_days": "calendar"
      },
      "discount": {
        "per_day_antecipated": {
          "calculation_type": "amount",
          "amount": 50,
          "calculation_days": "working"
        }
      }
    }
  },
  "options": {
    "authorization_type": "qrcode",
    "qrcode_expiration_seconds": 86400
  }
}
```

Every rule inside `due_detail` carries a `calculation_type`: with `amount`, send `amount` in cents; with `percentage`, send `value` in basis points (100 = 1%). Only `due_date` is required. The available rules are:

* **`fine`**: fine charged after the due date.
* **`interest`**: interest charged after the due date. `calculation_period` (`day`, `month`, `year`) and `calculation_days` (`calendar`, `working`) define how it accrues.
* **`discount.per_day_antecipated`**: discount per day paid in advance (`calculation_days`: `calendar` or `working`).
* **`discount.fixed_until_due`**: discount granted until each date listed in `amounts[]` (`{ "date", "amount" | "value" }`). Set only one of the two discount options.
* **`rebate`**: rebate applied to the amount.

> By setting `recurrence_required: false`, the payer can pay the first payment and still refuse the recurrence. With `true`, recurrence and first payment are approved together, in a single authorization.

**Journey C — Request sent straight to the payer's app**

Instead of generating a QR Code, the authorization request is sent directly to the payer's bank app. In this case, `counterparty.bank_account` is **required** — it is the account that receives the approval request.

```json
{
  "bank_account_id": "018af380-cedc-3a53-29c0-e329bf0e109b",
  "counterparty": {
    "tax_number": "70004764005",
    "name": "Jhon Doe",
    "bank_account": {
      "ispb": "49931906",
      "branch": "0001",
      "number": "12345678",
      "digit": "9"
    }
  },
  "description": "Annual plan",
  "contract_number": "CONTRACT-2025-003",
  "periodicity": "year",
  "start_date": "2025-11-01",
  "amounts": {
    "fixed": 59900
  },
  "options": {
    "authorization_type": "app"
  }
}
```

When the authorization goes through the app, Trio creates an **authorization request** (`recurrence request`), which you can follow with `load_requests` when reading the recurrence or through the `GET /v2/in/pix/recurrences/requests/{id}` endpoint. The request carries the `recurrence.id` it belongs to, the `counterparty` it was sent to and `expires_at`, the moment after which the payer can no longer answer it. The request statuses are: `created`, `sent`, `received`, `rejected`, `accepted`, `expired`, `cancelled`.

**Journey D — Variable amount with a minimum**

For subscriptions whose amount changes every cycle (consumption, usage, variable installments), inform only the minimum. The amount of each collection must be informed before it is sent.

```json
{
  "bank_account_id": "018af380-cedc-3a53-29c0-e329bf0e109b",
  "counterparty": {
    "tax_number": "70004764005",
    "name": "Jhon Doe"
  },
  "description": "Consumption bill",
  "contract_number": "CONTRACT-2025-004",
  "periodicity": "mnth",
  "start_date": "2025-11-01",
  "amounts": {
    "minimum": 1000
  },
  "options": {
    "authorization_type": "qrcode",
    "automatic_schedule": false,
    "automated_attempt_retry": true
  }
}
```

Amounts come back as money objects (`{ "amount", "currency" }`), the settings are grouped under `options`, the payer under `counterparty` and the authorization channel under `reference`.

### Options and settings at creation

The `options` block defines how the recurrence behaves over time. All fields are optional and have default values.

| Field                        | Default  | Description                                                                                                                                                                 |
| ---------------------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `authorization_type`         | `qrcode` | `qrcode` generates a QR Code; `app` sends the request directly to the payer's app (requires `counterparty.bank_account`).                                                    |
| `automatic_schedule`         | `true`   | Automatic management of collections. If `false`, each collection must be created and scheduled manually.                                                                    |
| `automated_attempt_retry`    | `true`   | Defines who manages the retries when a payment fails. If `true`, Trio manages the retries automatically. If `false`, they are the responsibility of the customer.            |
| `retry_policy`               | `3r_7d`  | Retry policy when a collection fails. `3r_7d`: 3 retries over 7 days, on alternating days. `none`: no retries.                                                              |
| `next_working_day`           | `false`  | If `true`, no collection happens on holidays; the collection moves to the payer's next working day.                                                                         |
| `qrcode_expiration_seconds`  | `86400`  | Expiration time (in seconds) of the dynamic QR Code. Ignored for static QR Codes.                                                                                           |

#### Automatic collection management

With `automatic_schedule: true` (default), Trio automatically creates and schedules each collection at the defined periodicity. You do not need to do anything each cycle — just react to the webhooks. Use this mode when the amount is fixed or when you can already determine the amount in advance.

With `automatic_schedule: false` (manual management), you are responsible for creating and scheduling each collection every cycle. This mode is needed, for example, when the variable amount is only known close to the collection date. See the [Collection management](#collection-management-collections) section.

#### Retries and customers who do not pay

The `retry_policy` defines what happens when a collection is not settled.

If `automated_attempt_retry` is sent as `true`, **Trio** is responsible for creating and managing these retries automatically. If it is sent as `false`, managing the retries is your application's responsibility.

* **`3r_7d`** — the collection is retried 3 times over 7 days, on alternating days. Each retry generates a new *attempt*. If no attempt is settled, the collection moves to a final failure or expiration status.
* **`none`** — there are no retries. A failed attempt ends the collection.

> **Cancelling the recurrence when the customer does not pay.** The retry policy works at the *collection* level, not the recurrence level. If your business rule is to end the subscription after an unpaid collection, monitor the *attempt* webhooks (`recurrence_collection_attempt` with type `failed` or `expired`) and/or the collection webhooks (`recurrence_collection` with type `expired` or `rejected`). When you detect that the retries are exhausted, call the recurrence cancellation endpoint to implement automatic cancellation for non-payment.

### Collection management (collections)

Each collection represents one debit occurrence of the recurrence. The lifecycle of a collection goes through the statuses: `created`, `active`, `settled`, `expired`, `rejected`, `cancelled`. Settlement attempts have the statuses: `requested`, `scheduled`, `settled`, `cancelled`, `rejected`, `expired`, `failed`.

#### Manual management: create the next collection

With `automatic_schedule: false`, create the next collection of the recurrence:

`POST: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections/next`

```json
{
  "recurrence_id": "0199d478-de39-fcf3-87a9-e8bded7db468"
}
```

The `201` response brings the created collection with its stages (`stages`) and attempts (`attempts`). The collection points to its recurrence through `recurrence.id`, and each stage records a status change with `error_code` / `error_message` when there is a rejection reason.

#### Schedule a collection (manual management)

Once created, the collection must be **scheduled** to be sent to the payer's bank. Scheduling must happen **between 2 and 10 days before** the cycle's payment date. When scheduling you can optionally inform the amount (for variable-amount recurrences), the due date and an `external_id`.

`POST: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections/{id}/schedule`

```json
{
  "amount": 12990,
  "due_date": "2025-11-01",
  "external_id": "COBR-2025-11"
}
```

* **`amount`**: amount in cents. Use it to inform/update the amount before scheduling. **It does not work on fixed-amount recurrences.**
* **`due_date`**: day the attempt is due (`YYYY-MM-DD`).
* **`external_id`**: your reference for the attempt.

The success response is `204 No Content`. Follow the result through the `recurrence_collection_attempt` webhook with type `scheduled` and, later, `settled` or `failed`.

#### Update the amount of a collection before it is sent

For **variable-amount** recurrences, you can update the amount of a collection that has not yet been sent to the payer's bank:

`PUT: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections/{id}`

```json
{
  "amount": 13500
}
```

* **`amount`**: new amount in cents.
* It is only possible to update while the collection has not been sent yet. In **fixed-amount** recurrences, the amount cannot be changed.

The success response is `204 No Content`. Read the collection back with `GET /v2/in/pix/recurrences/collections/{id}` to confirm the new `amount`.

#### Cancel a collection

You can cancel a specific collection (without cancelling the whole recurrence):

`POST: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections/{id}/cancel`

```json
{
  "requester_tax_number": "12345678000190",
  "entity_id": "019953ad-1738-b094-097c-7941a0c642a5"
}
```

* **`requester_tax_number`** (required): CPF/CNPJ of whoever is requesting the cancellation.
* **`entity_id`** (optional): entity identifier.

The success response is `204 No Content`. The collection moves to the `cancelled` status — you receive the `recurrence_collection.cancelled` webhook and can confirm it with a `GET`. The next collections of the recurrence continue normally.

### Cancelling the recurrence

To end the recurrence completely (no future collection will be generated):

`POST: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/{id}/cancel`

```json
{
  "requester_tax_number": "12345678000190"
}
```

* **`requester_tax_number`** (required): CPF/CNPJ of whoever requests the cancellation.

The success response is `204 No Content`. The recurrence moves to the `cancelled` status and you receive the `recurrence.cancelled` webhook.

### Queries

#### Get a recurrence

`GET: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/{id}`

Useful query parameters:

* **`load_stages`** (`true`/`false`): includes the recurrence's stage history.
* **`load_requests`** (`true`/`false`): includes the authorization requests (`app` journey).
* **`entity_id`**, **`group_id`**, **`bank_account_id`**: optional filters.

#### List recurrences

`GET: https://api.sandbox.trio.com.br/v2/in/pix/recurrences`

* **`from_datetime`** and **`to_datetime`** (required): time window.
* **`bank_account_id`**, **`entity_id`**: optional filters.
* **`limit`**, **`before`**, **`after`**: pagination.

#### Get an authorization request

`GET: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/requests/{id}`

Use `load_stages` to include the request's stages. `entity_id`, `group_id` and `bank_account_id` are optional filters.

#### Get and list collections

Get a specific collection, with stages and attempts:

`GET: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections/{id}`

* **`load_stages`** and **`load_attempts`**: include stages and attempts.
* **`entity_id`**, **`group_id`**, **`bank_account_id`**: optional filters.

List the collections of a recurrence:

`GET: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections`

* **`recurrence_id`** (required), **`from_datetime`** and **`to_datetime`** (required).
* **`entity_id`**: optional filter.
* **`limit`**, **`before`**, **`after`**: pagination.

#### Get and list attempts

List the attempts of a collection:

`GET: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections/attempts`

* **`recurrence_id`** and **`collection_id`** (required).
* `entity_id`, `from_datetime`, `to_datetime`, `limit`, `before`, `after`: optional.

Get a specific attempt:

`GET: https://api.sandbox.trio.com.br/v2/in/pix/recurrences/collections/attempts/{id}`

* **`load_stages`**: includes the attempt's stages.
* **`entity_id`**: optional filter.

Each attempt carries the `collection.id` it charges, its `due_date`, the Pix `end_to_end_id` and the `transaction_date` once it is paid.

### Webhooks

Asynchronous communication at each step happens through webhooks. There are three categories related to Pix Automático.

#### Recurrence — category `recurrence`

Fired on the state changes of the recurrence (the authorization "contract").

| Type        | Meaning                                                            |
| ----------- | ------------------------------------------------------------------ |
| `created`   | The recurrence was created.                                        |
| `approved`  | The recurrence was approved by the payer.                          |
| `rejected`  | The recurrence was rejected.                                       |
| `expired`   | The recurrence expired (authorization not completed in time).      |
| `cancelled` | The recurrence was cancelled.                                      |

[Payload example](/v2/webhooks/events/overview)

#### Collection — category `recurrence_collection`

Fired on the state changes of each collection.

| Type        | Meaning                                                      |
| ----------- | ------------------------------------------------------------ |
| `created`   | The collection was created.                                  |
| `active`    | The collection became active (scheduled/sent to the payer's bank). |
| `settled`   | The collection was settled.                                  |
| `expired`   | The collection expired.                                      |
| `rejected`  | The collection was rejected.                                 |
| `cancelled` | The collection was cancelled.                                |

#### Collection attempt — category `recurrence_collection_attempt`

Fired on each attempt to settle a collection. This is where you follow the actual result of the debit and the retries.

| Type        | Meaning                                          |
| ----------- | ------------------------------------------------ |
| `requested` | An attempt was created.                          |
| `scheduled` | The attempt was scheduled.                       |
| `settled`   | The attempt was settled (payment completed).     |
| `cancelled` | The attempt was cancelled.                       |
| `rejected`  | The attempt was rejected.                        |
| `expired`   | The attempt expired.                             |
| `failed`    | The attempt failed.                              |

### End-to-end flow summary

The table below ties each step of the process to the corresponding endpoint and webhook.

| Step                              | What you do                                                                                   | Expected webhook                                                         |
| --------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1. Create recurrence              | `POST /v2/in/pix/recurrences` and deliver the QR Code / send the request to the app           | `recurrence.created`                                                     |
| 2. Payer authorization            | (payer's action)                                                                              | `recurrence.approved` · `recurrence.rejected` · `recurrence.expired`     |
| 3a. Automatic collection          | nothing (automatic management)                                                                | `recurrence_collection.created` → `active`                               |
| 3b. Manual collection             | `POST .../collections/next` + `POST .../collections/{id}/schedule` (with `amount`/`due_date` if variable) | `recurrence_collection.created` → `active`                     |
| 4. Amount adjustment (variable)   | `PUT /v2/in/pix/recurrences/collections/{id}` before it is sent                               | —                                                                        |
| 5. Settlement                     | (processing)                                                                                  | `recurrence_collection_attempt.scheduled` → `settled`                    |
| 6. Failure / non-payment          | react according to `retry_policy`                                                             | `recurrence_collection_attempt.failed` · `recurrence_collection.expired` |
| 7. Cancel collection              | `POST /v2/in/pix/recurrences/collections/{id}/cancel`                                         | `recurrence_collection.cancelled`                                        |
| 8. Cancel recurrence              | `POST /v2/in/pix/recurrences/{id}/cancel`                                                     | `recurrence.cancelled`                                                   |

> **Best practice:** always handle the final states through webhooks (`settled`, `failed`, `expired`, `cancelled`) and use the queries (`GET`) for reconciliation. For non-payment, combine attempt monitoring with the `retry_policy` and decide, in your application, whether to cancel the recurrence.
