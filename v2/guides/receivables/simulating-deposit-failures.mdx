Besides validating input on your side, you should see how Trio behaves when a deposit is refused: a payer with an invalid CPF or CNPJ, a legal entity paying a code meant for individuals, a repeated payment of the same QR code. This guide turns on the bank account rules that reject or refund such deposits and pays a QR code against them.

## Before you start

The simulation uses the two-account setup from [Simulate a successful deposit](/v2/guides/receivables/simulating-deposit-success): one bank account generates the QR code and the other pays it. Read that guide first if you have not set the accounts up.

## Account rules

Each bank account carries a set of security and compliance rules that apply business logic and fraud prevention to incoming and outgoing transactions. In V2 they are exposed as the `parameters` object of the bank account. Read them with [`GET /v2/bank_accounts/{id}`](/v2/api-reference/banking-api/bank-accounts/get-bank-account) and toggle them with [`PUT /v2/bank_accounts/{id}`](/v2/api-reference/banking-api/bank-accounts/update-bank-account), which takes the boolean flags listed in the table:

```json
{
  "in_block_for_legal_entity": true,
  "in_block_for_pix_qrcode_different_amount_payment": true
}
```

| Rule ID | Rule | V2 parameter | Description |
| --- | --- | --- | --- |
| **1** | Block payins from unidentified individuals | `in_block_for_unidentified_deposit` | Rejects payments where the sender's identity could not be verified. |
| **2** | Block duplicated QR code payins | `in_block_for_pix_qrcode_duplicated_payment` | Prevents repeated payments using the same QR code. |
| **3** | Block payins with a different amount from the dynamic QR code amount | `in_block_for_pix_qrcode_different_amount_payment` | Ensures that the received amount matches the amount defined in the dynamic QR code. |
| **4** | Block payins from legal entities | `in_block_for_legal_entity` | Prevents receiving funds from companies (CNPJ), allowing only individuals (CPF). |
| **5** | Block payins from tax numbers different from the dynamic QR code tax number | `in_block_for_pix_qrcode_different_tax_number` | Ensures that the payer's tax number matches the one associated with the QR code. |
| **6** | Block payins from unauthorized participants | `in_block_for_unauthorized_participant` | Blocks payments from blacklisted participants. |
| **7** | Block payins from counterparty bank accounts different from the QR code | `in_block_for_pix_qrcode_different_counterparty_bank_account` | Verifies that the sender's bank account matches the account expected for the QR code payment. |
| **8** | Automatic refund for deposits incoming from minors | `automatic_refund_for_person_underage` | Automatically refunds deposits made by individuals under 18 years old. |
| **9** | Automatic refund for deposits incoming from deceased individuals | `automatic_refund_for_person_dead` | Automatically refunds payments made by individuals marked as deceased in official records. |
| **10** | Automatic refund for deposits incoming from individuals with invalid tax numbers | `automatic_refund_for_person_invalid_tax_number` | Automatically refunds payments from individuals with invalid CPF or CNPJ values. |
| **11** | Block payouts to legal entities (CNPJ) | `out_block_for_legal_entity` | Prevents outgoing payouts to companies, allowing payouts only to individuals. |

The V2 `parameters` object also carries an `out_blocked` flag, which has no counterpart in this table. Understanding these rules matters both for your integration and for testing the different transaction scenarios.

  <Step title="Create a QR code on that account">

    Paste the BR code in the Trio App as described in [Simulate a successful deposit](/v2/guides/receivables/simulating-deposit-success). The banking application shows the error below instead of settling the payment, which is what end users see in production:

  </Step>

## What you see on the Trio side

{/* TODO(v2): verify — which rules reject early in the payer's banking application is a business rule not described in the V2 spec */}

<Note>
Most payment failures happen during the initial validation, and the error goes straight back to the payer's banking application. In these cases no transaction record is created on the Trio side and your integration has nothing to handle. This early rejection applies to rules **1**, **2**, **5**, **6**, **8**, **9** and **10**.
</Note>

When a deposit is recorded on the Trio side, follow it through its `status` and `stages`, listed by [`GET /v2/documents/in`](/v2/api-reference/banking-api/documents/receivables/list-receivables), and through [webhook events](/v2/webhooks/events/overview). The [Document lifecycle](/v2/guides/pix/document-lifecycle) guide describes the statuses.
