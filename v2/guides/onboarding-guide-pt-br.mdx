Para solicitar a criação de um canal de distribuição, entre em contato com o Suporte da Trio ou com o seu Account Manager na Trio.

Este guia explica o fluxo de onboarding para uma integração em que uma organização atua como **distribuidora** das organizações dos seus clientes.

O processo permite que a organização distribuidora envie os dados necessários para abertura da conta do cliente, acompanhe a análise de Compliance por meio de webhooks e, após a aprovação, realize operações em nome da organização do cliente.

> **Importante:** este guia explica o fluxo e os conceitos envolvidos. Para consultar todos os campos, tipos e respostas disponíveis, veja a [referência da API de criação de onboarding](/v2/api-reference/banking-api/onboarding/create).

## 1. Como funciona o modelo de organização

Nesse modelo, existem duas partes principais:

- **Organização distribuidora:** organização que possui as credenciais de API e controla o fluxo dos seus clientes.
- **Organização do cliente:** organização criada durante o onboarding e que será utilizada para as movimentações do cliente.

O fluxo pode ser resumido assim:

```text
Organização distribuidora
        |
        | POST /v2/onboarding
        v
Criação do cliente
        |
        +--> Organização
        |
        +--> Entidade
        |
        +--> Dados do representante
        |
        v
Análise de Compliance
        |
        +--> in_review
        |
        +--> approved
        |
        └--> rejected
        |
        v
Organização aprovada
        |
        v
Operações via API usando
Trio-Target-Org-Id
```

A organização distribuidora continua utilizando suas próprias credenciais. Para executar uma operação na organização de um cliente, basta informar o identificador da organização de destino no header `Trio-Target-Org-Id`.

Consulte também [Acting on another organization](/v2/developers/authentication#acting-on-another-organization).

## 2. Criando o onboarding

O onboarding é criado através do endpoint:

```http
POST /v2/onboarding
```

No Sandbox:

```text
https://api.sandbox.trio.com.br/v2/onboarding
```

A autenticação utiliza **Basic Authentication**, com o `client_id` e `client_secret` da organização distribuidora.

```http
Authorization: Basic <encoded-value>
Content-Type: application/json
```

### Dados necessários

Para iniciar o onboarding, envie os dados da empresa, do representante e do consentimento.

| Campo | Descrição |
| --- | --- |
| `tax_number` | CNPJ da empresa que será cadastrada |
| `name` | Nome da entidade |
| `external_id` | Identificador externo utilizado pelo seu sistema (opcional) |
| `business_infos` | Informações comerciais da empresa |
| `representatives` | Dados do representante da empresa |
| `consent` | Dados do consentimento para abertura da conta |

Dentro de `business_infos`, os dois campos são obrigatórios e enviados como objetos monetários:

- `annual_revenue`: faturamento anual;
- `average_ticket`: ticket médio.

O representante deve possuir:

- `name`: nome;
- `tax_number`: CPF;
- `phone`: telefone no formato E.164;
- `email`: e-mail.

Cada representante também pode incluir dois campos opcionais de compliance. Ambos assumem `false` quando omitidos:

- `is_pep`: indica se o representante é uma pessoa politicamente exposta (PEP);
- `is_us_person`: indica se o representante é uma US person para fins fiscais.

O consentimento deve possuir:

- `tax_number`: CPF do representante legal responsável pelo consentimento;
- `ip_address`: endereço IP (IPv4 ou IPv6);
- `consent_at`: data e hora da autorização.

## 3. Exemplo de criação

```bash
curl --request POST \
  --url https://api.sandbox.trio.com.br/v2/onboarding \
  --header 'Authorization: Basic <encoded-value>' \
  --header 'Content-Type: application/json' \
  --data '{
    "tax_number": "61775921000110",
    "name": "Entity Test",
    "external_id": "12345ET",
    "business_infos": {
      "annual_revenue": {
        "amount": 500000,
        "currency": "BRL"
      },
      "average_ticket": {
        "amount": 10000000,
        "currency": "BRL"
      }
    },
    "representatives": [
      {
        "tax_number": "04969361908",
        "email": "john@gcorp.com",
        "phone": "+5541999990000",
        "name": "John",
        "is_pep": false,
        "is_us_person": false
      }
    ],
    "consent": {
      "tax_number": "04969361908",
      "ip_address": "8.8.8.8",
      "consent_at": "2026-08-25T07:00:00.000Z"
    }
  }'
```

Os valores monetários são enviados em centavos. Por exemplo:

```json
{
  "amount": 500000,
  "currency": "BRL"
}
```

representa R$ 5.000,00.

## 4. O que acontece depois da criação

A criação do onboarding é síncrona.

Após o processamento da requisição, a API retorna os principais identificadores da estrutura criada, incluindo:

- `entity_id`;
- `org_id`;
- `external_id`;
- `tax_number`;
- `name`;
- `status`.

A resposta também devolve os dados enviados na requisição (`business_infos`, `consent`, `representatives`), acrescentando o `id`, o `status` e os `required_documents` de cada representante.

Exemplo:

```json
{
  "data": {
    "entity_id": "01a0ee9f-7418-625f-e4b2-624b4ad4959f",
    "org_id": "92b0f620-7105-4c10-84a1-f5a034a14efa",
    "external_id": "404ANVIL",
    "tax_number": "61775921000110",
    "name": "ACME INC",
    "status": "in_validation",
    "business_infos": {
      "annual_revenue": {
        "amount": 5000000,
        "currency": "BRL"
      },
      "average_ticket": {
        "amount": 500000,
        "currency": "BRL"
      }
    },
    "consent": {
      "consent_at": "2026-08-25T07:00:00.000000Z",
      "ip_address": "8.8.8.8",
      "tax_number": "52998224725"
    },
    "representatives": [
      {
        "id": "8c61c7fd-3509-4306-9fec-9090e82fe121",
        "name": "Willy Coyote",
        "tax_number": "52998224725",
        "email": "w.coyote@acme.com",
        "phone": "+5541999990000",
        "status": "in_validation",
        "required_documents": ["identification"]
      }
    ],
    "required_documents": ["company_contract"],
    "inserted_at": "2026-09-29T19:23:42.485921Z",
    "updated_at": "2026-09-29T19:23:42.485921Z"
  }
}
```

> **Boa prática:** salve o `org_id`, `entity_id` e o `external_id` no seu sistema. O `org_id` será utilizado posteriormente para executar operações na organização do cliente.

### Documentos exigidos

A resposta inclui o campo `required_documents` em **dois lugares**, de acordo com os documentos configurados para o seu canal de distribuição:

- no nível da **entidade** (`data.required_documents`): os documentos que a empresa deve enviar, como `company_contract`, `power_of_attorney` e `financial_statement`;
- dentro de **cada representante** (`data.representatives[].required_documents`): os documentos que aquele representante deve enviar, normalmente `identification`.

{/* TODO(v2): verify — a especificação V2 declara os dois campos required_documents como arrays sem marcá-los como nullable; confirmar se a V2 retorna null ou um array vazio quando nenhum documento é exigido. */}
Ambos os campos retornam `null` quando nenhum documento é exigido. Utilize-os para saber exatamente quais documentos enviar na próxima etapa.

## 5. Envio de documentos da entidade e dos representantes

Dependendo da configuração do canal de distribuição, o Compliance pode exigir o envio de documentos de apoio para a entidade e/ou seus representantes. Os documentos são enviados **após** a criação do onboarding, utilizando os identificadores retornados por `POST /v2/onboarding`.

Cada documento é enviado individualmente através de:

```http
POST /v2/onboarding/documents
```

A requisição utiliza `multipart/form-data` e a mesma **Basic Authentication** da criação do onboarding. Somente arquivos **PDF** são aceitos.

### Campos

| Campo | Descrição |
| --- | --- |
| `reference_type` | `entity` ou `entity_representative` |
| `reference_id` | O `entity_id` (para `entity`) ou o `id` do representante (para `entity_representative`) |
| `document_type` | Classificação do documento (veja abaixo) |
| `file` | O arquivo PDF |

Tipos de documento por referência:

- **Entidade** (`reference_type: entity`): `company_contract`, `power_of_attorney`, `financial_statement`;
- **Representante** (`reference_type: entity_representative`): `identification`.

O `entity_id` e o `id` do representante são retornados na resposta de `POST /v2/onboarding`.

### Exemplo de envio

Enviando um balanço financeiro da entidade:

```bash
curl --request POST \
  --url https://api.sandbox.trio.com.br/v2/onboarding/documents \
  --header 'Authorization: Basic <encoded-value>' \
  --header 'Content-Type: multipart/form-data' \
  --form 'reference_type=entity' \
  --form 'reference_id=01a0ee9f-7418-625f-e4b2-624b4ad4959f' \
  --form 'document_type=financial_statement' \
  --form 'file=@./financial_statement.pdf'
```

Enviando um documento de identificação de um representante:

```bash
curl --request POST \
  --url https://api.sandbox.trio.com.br/v2/onboarding/documents \
  --header 'Authorization: Basic <encoded-value>' \
  --header 'Content-Type: multipart/form-data' \
  --form 'reference_type=entity_representative' \
  --form 'reference_id=8c61c7fd-3509-4306-9fec-9090e82fe121' \
  --form 'document_type=identification' \
  --form 'file=@./identification.pdf'
```

### Resposta

```json
{
  "data": {
    "id": "01a0ee9f-4ff4-e363-41fe-8ced18a18eef",
    "reference_type": "entity",
    "reference_id": "01a0ee9f-7418-625f-e4b2-624b4ad4959f",
    "document_type": "financial_statement",
    "inserted_at": "2026-09-29T19:23:33.236814Z",
    "updated_at": "2026-09-29T19:23:33.236814Z"
  }
}
```

> **Dica:** envie um documento por requisição. Repita a chamada para cada documento exigido da entidade e de cada representante. Consulte a [referência da API de envio de documentos](/v2/api-reference/banking-api/onboarding/create-document).

## 6. Etapa de liveness

Depois da criação, o onboarding segue para o processo de validação.

O representante precisa realizar o reconhecimento facial (**liveness**) necessário para a abertura da conta.

Exemplo:

```json
{
  "representatives": [
    {
      "id": "0191148f-b189-8e42-27a5-1368cc00dea8",
      "status": "in_review",
      "tax_number_linked": "11144477735",
      "name_linked": "John",
      "email": "john@gcorp.com",
      "liveness_link": "https://liveness.link/example?123"
    }
  ]
}
```

O cliente deve utilizar esse link para concluir a etapa de reconhecimento facial.

## 7. Análise de Compliance

Depois que o liveness for concluído, as informações do cliente seguem para análise de Compliance.

A organização distribuidora **não precisa ficar consultando a API continuamente** para saber se a análise terminou.

O acompanhamento deve ser feito pelos webhooks de entidade.

Os eventos da categoria `entity` são enviados quando o status de Compliance de uma entidade criada pelo onboarding é alterado.

Consulte a [referência de eventos de Entity](/v2/webhooks/events/overview).

## 8. Webhooks do onboarding

Os principais eventos relacionados ao onboarding são:

| Evento | Status | Descrição |
| --- | --- | --- |
| `entity.in_review` | `in_review` | Entidade está em análise de Compliance |
| `entity.approved` | `approved` | Entidade aprovada e pronta para operar |
| `entity.rejected` | `rejected` | Entidade rejeitada pela análise de Compliance |

### `entity.in_review`

Indica que a entidade entrou em análise.

## 9. Usando a organização do cliente

Depois que o onboarding for aprovado, a organização distribuidora pode realizar chamadas em nome da organização do cliente.

Para isso, utilize a mesma credencial da organização distribuidora e informe o `org_id` do cliente no header:

```http
Trio-Target-Org-Id: {target_org_id}
```

Exemplo:

```bash
curl https://api.sandbox.trio.com.br/v2/entities \
  -H "Content-Type: application/json" \
  -H "Trio-Target-Org-Id: 92b0f620-7105-4c10-84a1-f5a034a14efa" \
  -u {client_id}:{client_secret}
```

Nesse cenário:

```text
Credencial utilizada
        |
        v
Organização distribuidora
        |
        | Trio-Target-Org-Id
        v
Organização do cliente
        |
        v
Operação solicitada
```

O acesso é validado pela Trio a cada requisição. Se a organização distribuidora não possuir acesso à organização informada, a API retorna `403`.

> **Importante:** o acesso à organização é configurado no nível da organização e precisa estar habilitado para a integração.

## 10. Fluxo completo

O fluxo completo pode ser entendido da seguinte forma:

```text
1. Cliente solicita abertura da conta
              |
              v
2. Distribuidora coleta os dados
              |
              v
3. POST /v2/onboarding
              |
              v
4. Trio cria a organização e entidade
              |
              v
5. API retorna os identificadores
   - org_id
   - entity_id
              |
              v
6. Webhook: entity.in_review
              |
              v
7. Representante realiza o liveness
              |
              v
8. Compliance analisa os dados
              |
        +-----+-----+
        |           |
        v           v
   approved      rejected
        |           |
        v           v
9. Organização    Fluxo de
   pronta          tratamento
        |
        v
10. API com
    Trio-Target-Org-Id
        |
        v
11. Operações na
    organização do cliente
```

## 11. Recomendações para a integração

### Salve os identificadores

Após o `POST /v2/onboarding`, armazene no seu sistema pelo menos:

- `external_id`;
- `org_id`;
- `entity_id`;
- `tax_number`;
- status atual.

Isso facilita a reconciliação entre o seu sistema e a Trio.

### Use o `external_id` como referência do seu sistema

O `external_id` deve ser uma referência que permita identificar facilmente o cliente dentro da sua aplicação.

Exemplo:

```text
customer_12345
```

ou:

```text
company_98765
```

### Só habilite as operações após a aprovação

Mantenha o cliente em estado de onboarding enquanto o Compliance estiver analisando a entidade.

Após receber:

```text
entity.approved
```

o cliente pode seguir para as operações previstas na integração.

### Trate a rejeição

Quando receber:

```text
entity.rejected
```

armazene o `reason` retornado pelo webhook para permitir o tratamento adequado do cliente.

## Obtendo a conta bancária após a aprovação

{/* TODO(v2): verify — o prazo "em alguns minutos" é uma regra de negócio que não consta na especificação V2. A seção da V1 apontava para contas virtuais, que não existem na V2; agora aponta para GET /v2/bank_accounts. */}
Após a aprovação da entidade (`entity.approved`), a conta bancária do cliente costuma ficar disponível em alguns minutos. Ela não é criada no mesmo instante do evento de aprovação, então não assuma que o identificador da conta já estará disponível imediatamente.

Para obtê-la, chame o endpoint de [listagem de contas bancárias](/v2/api-reference/banking-api/bank-accounts/list-bank-accounts), informando o `org_id` do cliente no header:

```http
Trio-Target-Org-Id: {org_id}
```

Use essa chamada para listar as contas bancárias criadas para a organização do cliente e coletar o `id` da conta bancária (o `bank_account_id`) necessário para realizar transações em nome dele.

Este guia também está disponível em inglês: [/v2/guides/onboarding-guide](/v2/guides/onboarding-guide).
