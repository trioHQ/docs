This guide explains the onboarding flow for an integration in which an organization acts as an **distributor** for its customers' organizations.

The process allows the distributor organization to submit the data required to open the customer's account, track the Compliance analysis through webhooks and, once approved, perform operations on behalf of the customer's organization.

> **Important:** this guide explains the flow and the concepts involved. To check all available fields, types, and responses, see the [onboarding creation API reference](/v2/api-reference/banking-api/onboarding/create).

## 1. How the organization model works

In this model, there are two main parties:

- **Distributor organization:** the organization that holds the API credentials and controls the flow for its customers.
- **Customer organization:** the organization created during onboarding, which will be used for the customer's transactions.

The flow can be summarized as follows:

```text
Distributor organization
        |
        | POST /v2/onboarding
        v
Customer creation
        |
        +--> Organization
        |
        +--> Entity
        |
        +--> Representative data
        |
        v
Compliance analysis
        |
        +--> in_review
        |
        +--> approved
        |
        └--> rejected
        |
        v
Approved organization
        |
        v
Operations via API using
Trio-Target-Org-Id
```

The distributor organization continues to use its own credentials. To perform an operation on a customer's organization, simply provide the target organization's identifier in the `Trio-Target-Org-Id` header.

## 2. Creating the onboarding

Onboarding is created through the endpoint:

```http
POST /v2/onboarding
```

In Sandbox:

```text
https://api.sandbox.trio.com.br/v2/onboarding
```

Authentication uses **Basic Authentication**, with the distributor organization's `client_id` and `client_secret`.

```http
Authorization: Basic <encoded-value>
Content-Type: application/json
```

### Required data

To start onboarding, send the company's data, the representative's data, and the consent data.

| Field | Description |
| --- | --- |
| `tax_number` | Tax ID (CNPJ) of the company being registered |
| `name` | Entity name |
| `external_id` | External identifier used by your system (optional) |
| `business_infos` | Company business information |
| `representatives` | Company representative data |
| `consent` | Consent data for opening the account |

Within `business_infos`, both fields are required and sent as monetary objects:

- `annual_revenue`: annual revenue;
- `average_ticket`: average ticket.

The representative must have:

- `name`;
- `tax_number`: tax ID (CPF);
- `phone`: phone number in E.164 format;
- `email`.

Each representative can also include two optional compliance flags. Both default to `false` when omitted:

- `is_pep`: whether the representative is a politically exposed person (PEP);
- `is_us_person`: whether the representative is a US person for tax purposes.

The consent must have:

- `tax_number`: the tax ID (CPF) of the legal representative responsible for the consent;
- `ip_address`: IP address (IPv4 or IPv6);
- `consent_at`: date and time of the authorization.

## 3. Creation example

```bash
curl --request POST \
  --url https://api.sandbox.trio.com.br/v2/onboarding \
  --header 'Authorization: Basic <encoded-value>' \
  --header 'Content-Type: application/json' \
  --data '{
    "tax_number": "61775921000110",
    "name": "Entity Test",
    "external_id": "12345ET",
    "business_infos": {
      "annual_revenue": {
        "amount": 500000,
        "currency": "BRL"
      },
      "average_ticket": {
        "amount": 10000000,
        "currency": "BRL"
      }
    },
    "representatives": [
      {
        "tax_number": "04969361908",
        "email": "john@gcorp.com",
        "phone": "+5541999990000",
        "name": "John",
        "is_pep": false,
        "is_us_person": false
      }
    ],
    "consent": {
      "tax_number": "04969361908",
      "ip_address": "8.8.8.8",
      "consent_at": "2026-08-25T07:00:00.000Z"
    }
  }'
```

Monetary values are sent in cents. For example:

```json
{
  "amount": 500000,
  "currency": "BRL"
}
```

represents R$ 5,000.00.

## 4. What happens after creation

Onboarding creation is synchronous.

After the request is processed, the API returns the main identifiers of the structure that was created, including:

- `entity_id`;
- `org_id`;
- `external_id`;
- `tax_number`;
- `name`;
- `status`.

The response also echoes the data sent in the request (`business_infos`, `consent`, `representatives`), adding the `id`, `status`, and `required_documents` of each representative.

Example:

```json
{
  "data": {
    "entity_id": "01a0ee9f-7418-625f-e4b2-624b4ad4959f",
    "org_id": "92b0f620-7105-4c10-84a1-f5a034a14efa",
    "external_id": "404ANVIL",
    "tax_number": "61775921000110",
    "name": "ACME INC",
    "status": "in_validation",
    "business_infos": {
      "annual_revenue": {
        "amount": 5000000,
        "currency": "BRL"
      },
      "average_ticket": {
        "amount": 500000,
        "currency": "BRL"
      }
    },
    "consent": {
      "consent_at": "2026-08-25T07:00:00.000000Z",
      "ip_address": "8.8.8.8",
      "tax_number": "52998224725"
    },
    "representatives": [
      {
        "id": "8c61c7fd-3509-4306-9fec-9090e82fe121",

    "updated_at": "2026-09-29T19:23:42.485921Z"
  }

```

> **Best practice:** save the `org_id`, `entity_id`, and `external_id` in your system. The `org_id` will be used later to perform operations on the customer's organization.

### Required documents

The response includes a `required_documents` field in **two places**, based on the documents configured for your distribution channel:

- at the **entity** level (`data.required_documents`): the documents the company must provide, such as `company_contract`, `power_of_attorney`, and `financial_statement`;
- inside **each representative** (`data.representatives[].required_documents`): the documents that representative must provide, typically `identification`.

{/* TODO(v2): verify — the V2 spec declares both required_documents fields as arrays without marking them nullable; confirm whether V2 returns null or an empty array when no document is required. */}
Both fields are `null` when no document is required. Use them to know exactly which documents to upload in the next step.

## 5. Uploading entity and representative documents

Depending on the distribution channel configuration, Compliance may require supporting documents to be uploaded for the entity and/or its representatives. Documents are sent **after** the onboarding is created, using the identifiers returned by `POST /v2/onboarding`.

Each document is uploaded individually through:

```http
POST /v2/onboarding/documents
```

The request uses `multipart/form-data` and the same **Basic Authentication** as the onboarding creation. Only **PDF** files are accepted.

### Fields

| Field | Description |
| --- | --- |
| `reference_type` | `entity` or `entity_representative` |
| `reference_id` | The `entity_id` (for `entity`) or the representative `id` (for `entity_representative`) |
| `document_type` | Document classification (see below) |
| `file` | The PDF file |

Document types by reference:

- **Entity** (`reference_type: entity`): `company_contract`, `power_of_attorney`, `financial_statement`;
- **Representative** (`reference_type: entity_representative`): `identification`.

The `entity_id` and the representative `id` are both returned in the `POST /v2/onboarding` response.

### Upload example

Uploading a financial statement for the entity:

```bash
curl --request POST \
  --url https://api.sandbox.trio.com.br/v2/onboarding/documents \
  --header 'Authorization: Basic <encoded-value>' \
  --header 'Content-Type: multipart/form-data' \
  --form 'reference_type=entity' \
  --form 'reference_id=01a0ee9f-7418-625f-e4b2-624b4ad4959f' \
  --form 'document_type=financial_statement' \
  --form 'file=@./financial_statement.pdf'
```

Uploading an identification document for a representative:

```bash
curl --request POST \
  --url https://api.sandbox.trio.com.br/v2/onboarding/documents \
  --header 'Authorization: Basic <encoded-value>' \
  --header 'Content-Type: multipart/form-data' \
  --form 'reference_type=entity_representative' \
  --form 'reference_id=8c61c7fd-3509-4306-9fec-9090e82fe121' \
  --form 'document_type=identification' \
  --form 'file=@./identification.pdf'
```

### Response

```json
{
  "data": {
    "id": "01a0ee9f-4ff4-e363-41fe-8ced18a18eef",
    "reference_type": "entity",
    "reference_id": "01a0ee9f-7418-625f-e4b2-624b4ad4959f",
    "document_type": "financial_statement",
    "inserted_at": "2026-09-29T19:23:33.236814Z",
    "updated_at": "2026-09-29T19:23:33.236814Z"
  }
}
```

> **Tip:** upload one document per request. Repeat the call for each required document of the entity and of each representative. See the [upload document API reference](/v2/api-reference/banking-api/onboarding/create-document).

After creation, onboarding moves on to the validation process.

The representative needs to complete the facial recognition (**liveness**) check required to open the account.

Example:

## 7. Compliance analysis

Once liveness is completed, the customer's information moves on to Compliance analysis.

The distributor organization **does not need to keep polling the API** to find out whether the analysis has finished.

Tracking should be done through entity webhooks.

Events in the `entity` category are sent whenever the Compliance status of an entity created through onboarding changes.

See the [Entity events reference](/v2/webhooks/events/overview).

## 8. Onboarding webhooks

The main events related to onboarding are:

| Event | Status | Description |
| --- | --- | --- |
| `entity.in_review` | `in_review` | The entity is under Compliance analysis |
| `entity.approved` | `approved` | The entity has been approved and is ready to operate |
| `entity.rejected` | `rejected` | The entity was rejected by Compliance analysis |

## 9. Using the customer's organization

Once onboarding has been approved, the distributor organization can make calls on behalf of the customer's organization.

To do this, use the same credentials as the distributor organization and provide the customer's `org_id` in the header:

```http
Trio-Target-Org-Id: {target_org_id}
```

Example:

```bash
curl https://api.sandbox.trio.com.br/v2/entities \
  -H "Content-Type: application/json" \
  -H "Trio-Target-Org-Id: 92b0f620-7105-4c10-84a1-f5a034a14efa" \
  -u {client_id}:{client_secret}
```

In this scenario:

```text
Credentials used
        |
        v
Distributor organization
        |
        | Trio-Target-Org-Id
        v
Customer organization
        |
        v
Requested operation
```

Access is validated by Trio on every request. If the distributor organization does not have access to the specified organization, the API returns `403`.

> **Important:** access to the organization is configured at the organization level and must be enabled for the integration.

## 10. Complete flow

The complete flow can be understood as follows:

```text
1. Customer requests account opening
              |
              v
2. Distributor collects the data
              |
              v
3. POST /v2/onboarding
              |
              v
4. Trio creates the organization and entity
              |
              v
5. API returns the identifiers
   - org_id
   - entity_id
              |
              v
6. Webhook: entity.in_review
              |
              v
7. Representative completes liveness
              |
              v
8. Compliance analyzes the data
              |
        +-----+-----+
        |           |
        v           v
   approved      rejected
        |           |
        v           v
9. Organization   Handling
   ready           flow
        |
        v
10. API with
    Trio-Target-Org-Id
        |
        v
11. Operations on the
    customer's organization
```

## 11. Integration recommendations

### Save the identifiers

After `POST /v2/onboarding`, store at least the following in your system:

- `external_id`;
- `org_id`;
- `entity_id`;
- `tax_number`;
- current status.

This makes it easier to reconcile your system with Trio.

### Use `external_id` as your system's reference

The `external_id` should be a reference that lets you easily identify the customer within your application.

Example:

```text
customer_12345
```

or:

```text
company_98765
```

### Only enable operations after approval

Keep the customer in an onboarding state while Compliance is analyzing the entity.

After receiving:

```text
entity.approved
```

the customer can move on to the operations supported by the integration.

### Handle rejections

When you receive:

```text
entity.rejected
```

store the `reason` returned by the webhook so the customer's case can be handled appropriately.

## Retrieving the bank account after approval

{/* TODO(v2): verify — the "available within a few minutes" timing is a business rule not described in the V2 spec. The V1 section pointed to virtual accounts, which have no V2 equivalent; it now points to GET /v2/bank_accounts. */}
Once the entity is approved (`entity.approved`), the customer's bank account is typically made available within a few minutes. It is not created at the exact same instant as the approval event, so you should not assume the account identifier is available immediately.

To retrieve it, call the [list bank accounts](/v2/api-reference/banking-api/bank-accounts/list-bank-accounts) endpoint, passing the customer's `org_id` in the header:

```http
Trio-Target-Org-Id: {org_id}
```

Use this call to list the bank accounts created for the customer's organization and collect the bank account `id` you'll need (as `bank_account_id`) in order to perform transactions on their behalf.
